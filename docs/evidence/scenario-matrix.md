## Interpretation

`READY_TO_RUN` means an executable fixed assertion exists in the repository but this document does not pretend it was executed by a particular environment. `PROPERTY_TEST` means generated local invariant checks; Rust failures preserve proptest counterexamples/seeds and gateway generators use fixed seeds. Property tests are not live T3N evidence and their case count is not a coverage percentage. `NOT_RUN` means the scenario intentionally requires real T3N testnet state, credentials, credits and, for egress scenarios, seeded private remediation/verification configuration.

For Member Delegation status, `ACTIVE` means the observed grant is currently inside its validity window. A grant whose `valid_from_secs` is in the future is `SCHEDULED` and does not make the control plane ready. Expired grants are `REVOKED`; malformed, non-numeric or inverted validity windows are `UNKNOWN` and fail closed. Proposal and Executor grants are evaluated independently under the same temporal semantics.

Member grant state and effective T3N access are different controls. The grant document answers what the tenant configured; it is not treated as the final authorization verdict. The authenticated Proposal Agent and Protected Executor each execute `checkDelegation` with the canonical tenant DID plus the exact contract, functions and minimum scopes assigned to that principal. `authorised=true` can become effective `ACTIVE` only when the corresponding Member grant is also `ACTIVE`. `authorised=false` is `DENIED`; exceptions or unexpected results are `UNKNOWN`. `DENIED` and `UNKNOWN` fail closed in gateway, backend, frontend and live evidence.

The Proposal Agent receives only `evaluate-action` and no protected-egress hosts. The Protected Executor uses a different authenticated T3N credential/DID and receives only `execute-remediation` and `verify-remediation` plus the minimum required egress hosts. The live negative evidence separately attempts both privileged functions with the Proposal Agent session and also mutates/restores each Member grant to prove the exact principal-side `checkDelegation` becomes negative after revocation. A human remediation capability remains required at the application/gateway boundary and is bound to the authenticated Executor DID, so replacing the executor after authorization invalidates execution.

The destination allowlist and the operator-approved destination are also separate controls. A policy may allow hosts A and B, but a capability approved for A cannot be changed to B in transit, and private KV resolution to B cannot reuse the old approval. The controlled `L16` live scenario is testnet-only, adds B to the Executor grant only while that scenario is enabled, requires both A and B to be policy-allowed, and records PASS only when the contract blocks B before HTTP. `NOT_RUN` remains non-evidence.

`ALLOW` is a policy result, not proof that an execution capability exists for that action. The protected executor and independent completion contract are closed to two implemented actions: `revoke-credential`, whose final verified state is `REVOKED`, and `notify-security`, whose final verified state is `DELIVERED` plus `recipient_resolved=true`. `isolate-account` and `create-incident` remain valid policy-evaluation actions, but Spring authorization and Rust `execute-remediation` fail closed before side effects if either is sent to the remediation executor.

For `notify-security`, the application and model carry only the logical private reference `verified_email`. The Rust/WASM contract maps that reference to the T3N profile marker only inside the protected execution boundary and sends it through `http-with-placeholders`. The contract result and evidence bundle expose only delivery metadata; the marker and resolved recipient value are not returned. `L11` is executable but remains `NOT_RUN` until explicitly enabled with a synthetic verified profile and controlled endpoints. It may be recorded as `PASS` only when independent read-back returns the exact operation, `DELIVERED`, and `recipient_resolved=true`.

`execute-remediation` returning 2xx is only an **acceptance signal**. It is represented as `PENDING_VERIFICATION`. `COMPLETED` is reserved for the Spring state machine after `verify-remediation` independently observes the action-specific closed expected state and any action-specific private-resolution assertion. A timeout or ambiguous acknowledgement is `UNVERIFIED` and never triggers automatic re-execution.

`requestId` is propagated as the stable logical idempotency key. The project does not claim exactly-once or at-most-once behavior from an external provider unless that provider explicitly honors the key. The local atomic claim prevents this application from intentionally initiating a second egress for the same action.

The generated `docs/evidence/testnet-run.json` is the source of truth for actual live results. It records sanitized Proposal/Executor Member/effective states plus the exact checked functions/scopes, and never persists full grant documents, credentials, profile markers or resolved profile values. It is written only after leak detection checks configured tenant/proposal/executor/provider/service/capability/remediation secrets. Negative delegation scenarios count as `PASS` only when the returned failure is recognizably authorization/delegation related or, for the explicit `checkDelegation` revocation scenarios, when the SDK returns `authorised=false`; an inconclusive response, missing secret, transport failure or unrelated runtime exception is recorded as `FAIL`.
